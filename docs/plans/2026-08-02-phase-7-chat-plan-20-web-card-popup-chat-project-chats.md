# Plan 20: Web UI — Card Popup Chat Tab + Project Chats Tab + Context-Aware ChatDock + CardChatLinkList + Card Linking
**Branch:** `task/web-card-popup-chat-project-chats`
**Parent branch:** `feat/phase-7-chat`
**Parent spec:** `2026-08-02-phase-7-chat-design.md` — Task 20

> **Renamed 2026-08-06 (was "CardChatLinkList + Chat Pages").** Scope broadened per design session: the card-detail surface is now a multi-popup (`CardPopup`, infra landed in Plan 19b) rather than a single `CardModal`; chat visibility changes from owner-only to "sessions the user participated in" (owner OR project member); the project view gains a "Chats" tab; the card popup gains a "Chat" tab; and the `ChatDock` becomes context-aware (detects `currentProjectId` + `currentCardId` from where it was opened) with a manual card-linking button. `@mention` card linking is deferred to V2 (noted in spec §5.4).

**Goal:** Adopt the Plan-19b popup shell for cards; add a "Chat" tab to the card popup showing linked chats (`CardChatLinkList`); add a "Chats" tab to the project view (All / Project / Card filter); make the `ChatDock` context-aware; add a manual "link this card to the current session" button inside the dock; broaden the chat-session list query to sessions the caller participated in (owner OR project member) via an in-place upgrade that preserves existing sessions.

## Decisions (from session)

- **Q2 — Chat visibility:** Option 3. `GET /api/chat/sessions` lists sessions the caller **participated in** — i.e. sessions they own **or** project chats where they are a `ProjectMember` (admin bypass). Not "all project chats in projects I'm a member of" (that would leak chats the user never took part in); a session counts as "participated in" if the caller is its owner, or the caller is a member of the session's project. This is an in-place upgrade of `ChatSessionService.ListAsync` + `IChatSessionRepository.ListAsync`/`CountAsync`/`SearchByTitleAsync` — no data migration, existing sessions keep their `OwnerId`/`ProjectId`.
- **Q2-secondary — PersonalChat → ProjectChat migration:** Option (b), upgrade in-place to preserve story. The listing/visibility change is a query broadening, not a reclassification — no session is rewritten, no `AiFeature` flip, no data backfill. Existing personal chats stay personal; existing project chats stay project. The only change is which sessions appear in the caller's list.
- **Q2 — Project "Chats" tab:** New tab in `pages/projects/[projectId]/index.vue` board view. Filter: All / Project / Card (Card = chats linked to a card in this project via `CardChatLink`). Reuses the same `GET /api/chat/sessions?projectId=…` backend; the "Card" filter is a client-side grouping over `CardChatLink` lookups (or a new optional `?cardLinked=true` query — see step below; prefer reusing existing endpoints and grouping client-side to avoid a new backend endpoint in this plan).
- **Q2 — Card popup "Chat" tab:** New tab in the card popup (the migrated `CardModal` body). Shows `CardChatLinkList` (linked chats for this card). Any project member can interact (open a linked session, send messages) — same auth as the session itself (owner OR project member). Owner-clickable row opens the session (full if owner, read-only if not — matches existing `CardChatLinkList` contract).
- **Q2 — Context-aware ChatDock:** The dock already derives `currentProjectId` from the route and reads `useBoardStore().openCardId` as the card context (see `stores/chatDock.ts:124`). This plan makes the context explicit and origin-aware: opening the dock from the project "Chats" tab sets `currentProjectId`, no card; opening from a card popup's "Chat" tab sets `currentProjectId` + `currentCardId`; opening from the board header toggle sets `currentProjectId` only. The dock's "new session" call uses whichever context is active.
- **Q2 — Card linking button (MVP):** A button inside the `ChatDock` (session mode) that links the current session's `OpenCardId` to the active card (`currentCardId`), when both are set and the session is project-scoped. Calls a new lightweight endpoint or reuses the existing session-update path (see step). This is the manual MVP for linking a chat to a card; `@mention`-based auto-linking is V2 (deferred — noted in spec §5.4 and §11).
- **Q1 — Escape:** handled by Plan 19b's shared composable (LIFO across card popups + dock). No new Escape logic here.
- **Q3 — Max cards:** enforced by Plan 19b's store. This plan just calls `cardPopup.openCard(cardId)`; the 4th-open toast comes from the store.

## Steps

- [ ] **Backend — list visibility (in-place upgrade).** Broaden `IChatSessionRepository.ListAsync`/`CountAsync`/`SearchByTitleAsync`: the candidate set is `sessions WHERE OwnerId = @actor OR (ProjectId IS NOT NULL AND ProjectId IN (SELECT ProjectId FROM project_member WHERE UserId = @actor))`, then apply the existing `folderId`/`projectId`/`before`/`limit`/status filters. Admin bypass: admins see all project chats for any project (existing admin-bypass pattern). No `AiFeature` change, no data migration. Add/extend Application tests: owner's personal chats still listed; project chat where caller is a member (not owner) now listed; project chat where caller is neither owner nor member is not listed; admin sees all project chats.
- [ ] **Backend — card linking.** Add `LinkCardAsync(sessionId, cardId, actorId)`: load session, require `Status=Active`, require `ProjectId != null` (project-scoped), membership guard (owner OR project member, admin bypass), validate `cardId` belongs to `session.ProjectId` (`CHAT_CARD_NOT_IN_PROJECT`), set `session.OpenCardId = cardId` via an entity method (e.g. `session.SetOpenCard(cardId)` — add to `ChatSession` if not present; do not set the property directly). Expose `POST /api/chat/sessions/{sessionId}/link-card` `{ cardId }` → `ChatSessionDto`. Idempotent (linking the same card again is a no-op success). Add Application + integration tests.
- [ ] **`CardChatLinkList.vue`:** collapsible summary table. Fetches `GET ApiRoutes.Cards.chatLinks(cardId)`. Columns: owner (username), summary, created, actions (open). Owner-clickable row → opens the session: full `ChatSessionView` if the caller is the owner, read-only (messages render, input hidden) if not. Reuse `useApi()` try/catch (D-40) + `useAppToast` for fetch errors.
- [ ] **Migrate `CardModal.vue` body into `CardPopup.vue` slot.** Move the `UTabs` body (details/checklist/comments/related/docs) + all child panels (`CardDescription`, `CardMetadata`, `CardChecklist`, `CardComments`, `CardDependencies`, `CardSpec`, `CardPlan`, `CardAttachments`) into the `CardPopup` default slot. Preserve the version-ownership pattern (D-41): the popup instance owns the single `card` ref + `card.version`; panels emit `'update:card'` with the server response. Add the new "Chat" tab (`activeTab` gains `'chat'`; `tabs`/`desktopTabs` gain `{ label: 'Chat', value: 'chat' }`) hosting `CardChatLinkList`. Retire the old `AppModal`-based `CardModal` shell.
- [ ] **Board open path.** `BoardCard.vue` open action → `cardPopup.openCard(cardId)` (Plan 19b store). Also call `setOpenCardId(cardId)` so the existing realtime bridge + dock context keep working. Remove the `CardModal` mount from the board page; the `CardPopupLayer` (Plan 19b, mounted in `layouts/default.vue`) renders the popups.
- [ ] **Project "Chats" tab.** Add a "Chats" tab to `pages/projects/[id]/index.vue` (alongside the board). Lists project chats the caller participated in (reuses the broadened `GET /api/chat/sessions?projectId=…`). Filter bar: All / Project / Card. "Card" filter groups by linked `CardChatLink` — fetch `CardChatLink` per card in the project (or fetch all sessions then group client-side by a `cardChatLinks` lookup; prefer the latter to avoid N calls). Clicking a session opens the `ChatDock` with `openOrigin='project-chats'`, `currentProjectId` set, no card.
- [ ] **Context-aware `ChatDock`.** Add `currentCardId` (computed from `cardPopup.activeCardId` when on a project page) and `openOrigin` to `stores/chatDock.ts`. The "new session" request body includes `projectId` + `openCardId` per origin: `board` → project only; `card-popup` → project + card; `project-chats` → project only. The dock's open action is called by each origin with the right `openOrigin` (board header toggle, card-popup Chat tab "new chat" button, project-chats tab row click).
- [ ] **`ChatLinkCardButton.vue`:** shown in `ChatDock` session-mode header when `currentCardId` is set, the active session is project-scoped, and `session.OpenCardId !== currentCardId`. Calls `POST ApiRoutes.Chat.linkCard(sessionId, currentCardId)` (try/catch D-40). On success: toast + update the dock's session ref (`OpenCardId` changed) so the button hides. On `CHAT_CARD_NOT_IN_PROJECT`: error toast.
- [ ] **Spec update.** Apply the §2.1/§5.1/§5.2/§5.4 reconciled notes (this plan's parent commit adds them; this step confirms the spec matches the shipped behavior before close).
- [ ] **Manual validation:** `docs/manual-validation/2026-08-02-phase-7-chat-plan-20-web-card-popup-chat-project-chats-matrix.md` — (1) open a card from the board → it opens as a `CardPopup` (not the old modal); open a 2nd + 3rd → three popups coexist; a 4th is rejected with a toast. (2) Card popup "Chat" tab shows `CardChatLinkList` after a project chat closes; a non-owner project member can open a linked session read-only and send messages. (3) Project "Chats" tab lists chats the user participated in (own + project-member), All/Project/Card filters work. (4) Open the dock from the card-popup Chat tab → new session is project+card scoped; the "link this card" button appears and links successfully; `@mention` linking is NOT present (V2). (5) Escape closes popups LIFO (dock + cards). (6) Existing personal chats still appear in `pages/chats/index.vue` after the list-visibility change (no regression).

- A dedicated `?cardLinked=true` backend filter for the project "Chats" tab — this plan groups client-side to avoid a new endpoint.
