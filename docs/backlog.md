# Backlog

Ideas and enhancements outside the current phase scope. Not committed — revisit during phase planning.

- **Admin-configurable Kanban column templates** — Partially resolved: `ColumnTemplates` (Software/General/Blank) replaced the old static `DefaultColumnNames` array and ships today, but the three templates are still compile-time constants. Still open: let an admin edit/add templates at runtime (via `SystemSettings` or a new `ProjectTemplate` entity) — name, order, WIP limits, color per template.
- **Floating card windows** — replace UModal-based card detail with draggable, resizable windows (one per card). Enables multi-card view (see two cards side-by-side, reference one while editing another). Close per-window. Potential libs: `vue-draggable-resizable`, native `useDraggable` from `@vueuse/core`. Would replace CardModal with a window manager component.
- **Keyboard navigation for projects page** — add `useRovingFocus`-based keyboard nav to the project list table (arrow keys, Enter to open, shortcuts for edit/archive). Currently the board page has full keyboard nav but the projects list doesn't.
- **Per-user notification preferences** — Plan 7 (`docs/archive/plans/2026-07-25-phase-5-notifications-admin-plan-7-notification-triggers.md`) wires 7 fixed triggers (card move/assign, comment, @mention, dependency resolved, project archive/update) with no opt-out. Every recipient in the computed set (assignees, watchers, or all project members depending on trigger) always gets notified — no way for a user to mute a card, a project, or a trigger type. Would need a `NotificationPreference` entity (per-user, possibly per-project/per-card) checked inside `NotificationService.NotifyAsync` before the DB write + ntfy push.
- **Self-service password change** — `POST /api/Auth/change-password` was never built (see functional-spec Phase 3 checklist). Phase 5 shipped admin-initiated `POST /api/admin/users/{id}/reset-password` only; a user still can't change their own password without admin intervention.
- **`UAvatar` blank fallback in Phase 3 components** — `ProjectCreateModal.vue`, `ProjectEditModal.vue`, `MemberManagementPanel.vue` bind `:username="..."`, and `CardComments.vue` binds `:name="..."` — neither is a real `UAvatar` prop in Nuxt UI v4 (only `src`/`alt`/`icon`/`text` exist), so those avatars silently render blank instead of initials. Same root cause fixed in the chat components (`ChatMessageBubble.vue`/`ChatMessageList.vue` used `:name="..."` too) — swap to `:text="getInitials(...)"`.
- **Hard-delete for `LlmProvider`** — Admin can only `Disable` a provider (`IsEnabled = false`); there's no delete endpoint at all. A misconfigured provider (wrong `AdapterType`, which is immutable post-create by design) can't be removed, only disabled forever, forcing the admin to re-add under a different name and leave the mistake visible in the list permanently. Needs a real `DELETE /api/admin/providers/{id}` — likely hard-delete given `LlmProvider` has no `ArchivedAt`/housekeeping lifecycle (unlike user-content entities), guarded against providers referenced by `FeatureRoutingConfig`/`FeatureAllowedModel` or historical `TokenUsageRecord`/`ImageUsageRecord` rows (FK behavior needs deciding — block delete vs. null out the reference).
- **"PR created" notification trigger** — Phase 5's notification-rules design (`docs/archive/specs/phase-5-multi-user-notifications-admin.md`) lists "PR created → all members" alongside the 7 triggers Plan 7 actually wired, but Git/PR integration is out of scope for Phase 5 (no PR event source exists). Revisit once Phase 8's Git Agent lands.
- **Docs tab has no realtime/BoardHub wiring** — the server side already does its part: `ProjectDocumentService.CreateAsync`/`UpdateAsync`/`RestoreVersionAsync` all publish a `ProjectBoardEventEnvelope` with `BoardEntityType.ProjectDocument` via `IProjectBoardEventPublisher`, same as every other board entity. But `ProjectDocuments.vue` never calls `useRealtime()`/subscribes to those events — unlike `ProjectBoard.vue`, which routes `BoardEntityType.Card`/`Column` events into targeted store patches (see `useRealtime.ts` conventions in CLAUDE.md). So if one tab/user edits or restores a project document, another tab/user sitting on the Docs tab won't see it update until they manually reload. Fix is client-only: give `ProjectDocuments.vue` a realtime subscription that reacts to `ProjectDocument` events — likely a full `fetchDocuments()` refresh (rare event, small list) rather than a targeted single-doc patch, mirroring the `CardRelationship`-event handling precedent (full refresh accepted for low-frequency events).
