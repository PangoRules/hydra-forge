### Code review findings

#### [HIGH] No rate limiting on any endpoint
- **Category:** Rate limiting / DoS resilience
- **Where:** Entire API surface — `Program.cs` has no `AddRateLimiter()` call. Login at `POST /api/auth/login`, all project/card CRUD endpoints, SignalR hubs.
- **Issue:** Zero rate limiting configured anywhere. Login endpoint is brute-forceable — attacker can attempt unlimited password guesses. All list endpoints accept unbounded pagination parameters. No request body size limits beyond the single `[RequestSizeLimit]` on attachments.
- **Impact:** Brute-force credential stuffing on login. DoS via rapid-fire expensive queries (card lists with large `archivedLimit`, project lists with large `take`). No protection against automated abuse of any endpoint.
- **Fix:** Add `builder.Services.AddRateLimiter()` with a fixed-window or token-bucket policy. Apply `[EnableRateLimiting]` globally, with stricter limits on `POST /api/auth/login` (e.g. 5 attempts per minute per IP). Add `[RequestSizeLimit]` or global `MaxRequestBodySize` on all POST/PUT endpoints.

#### [HIGH] PresenceHub FocusCard/UnfocusCard lack project membership check
- **Category:** Broken authentication / authorization
- **Where:** `src/HydraForge.Server/Hubs/PresenceHub.cs:85-109` — `FocusCard()` and `UnfocusCard()` methods
- **Issue:** `JoinProject()` correctly verifies membership before adding the caller to the SignalR group. But `FocusCard()` and `UnfocusCard()` broadcast to `Clients.OthersInGroup(groupName)` without verifying the caller is actually a member of that project. An authenticated user who has joined project A can call `FocusCard(projectBId, cardId)` and the event broadcasts to project B's members — even though the caller never joined project B's group and has no access to it.
- **Impact:** Authenticated user can spoof card-focus presence events into any project on the instance. Leaks the fact that a card ID exists in a target project. Could be used to harass users or disrupt collaboration UI by flooding fake focus events.
- **Fix:** Add membership check at the top of `FocusCard()` and `UnfocusCard()` — same pattern as `JoinProject()`: check admin role, then verify `_memberRepo.GetByProjectAndUserAsync(projectId, userId)` is non-null. Throw `HubException("Access denied")` on failure.

#### [HIGH] No brute-force protection on login
- **Category:** Rate limiting / DoS resilience
- **Where:** `src/HydraForge.Application/Auth/LoginUserHandler.cs:71-101`
- **Issue:** `LoginUserHandler.HandleAsync()` validates credentials with no tracking of failed attempts. No account lockout, no incremental delay, no CAPTCHA integration. An attacker can submit unlimited login attempts.
- **Impact:** Credential stuffing / dictionary attacks against user accounts. Admin account especially high-value target since admin seed credentials are documented in committed config files.
- **Fix:** Track failed login attempts per user (or per IP for non-existent users) with exponential backoff. Lock account after N consecutive failures (e.g. 5) for a cooldown period (e.g. 15 minutes). Log all failed attempts to audit log. Combine with rate limiting on the login endpoint.

#### [HIGH] Committed dev secrets in appsettings.Development.json
- **Category:** Secrets exposure
- **Where:** `src/HydraForge.Server/appsettings.Development.json` — lines 3, 15-16, 24, 28-29
- **Issue:** Real credentials committed to git: DB password (`hydr4l0c4`), MinIO access/secret keys (`minioadmin`/`minioadmin`), JWT signing key (`5ae089b3...`), admin seed credentials (`admin`/`admin`). While `.env` is gitignored, `appsettings.Development.json` is tracked and contains live dev secrets.
- **Impact:** If the repository ever becomes public (or an unauthorized party gains read access), these credentials expose the dev environment. The JWT signing key allows token forgery for the dev instance. The MinIO credentials are defaults but still grant access to dev file storage.
- **Fix:** Move all secrets to environment variables or user secrets (`dotnet user-secrets`). Replace values in `appsettings.Development.json` with placeholder tokens (`"**OVERRIDE-VIA-ENV**"`). Add `appsettings.Development.json` to `.gitignore` and provide `appsettings.Development.example.json` instead. Rotate the committed JWT signing key and DB password.

#### [MEDIUM] Default JWT signing key placeholder in production config
- **Category:** Weak cryptography / Insecure configuration
- **Where:** `src/HydraForge.Server/appsettings.json:24` — `"SigningKey": "your-256-bit-secret-key-here-replace-in-production"`
- **Issue:** The base `appsettings.json` contains a well-known placeholder signing key. `Program.cs:84-86` throws if the key is missing entirely, but does not validate that it has been changed from the default. If an operator deploys without overriding `Jwt:SigningKey` via environment variable, all JWTs are signed with a publicly documented key.
- **Impact:** Any JWT can be forged. Attacker can impersonate any user, including admin. Complete auth bypass.
- **Fix:** Add startup validation that rejects the known placeholder value. Example: `if (jwtSigningKey == "your-256-bit-secret-key-here-replace-in-production") throw new InvalidOperationException("Jwt:SigningKey must be changed from the default placeholder.");`. Alternatively, remove the default from `appsettings.json` entirely and make the env var required with no fallback.

#### [MEDIUM] Unbounded pagination on multiple endpoints
- **Category:** Rate limiting / DoS resilience
- **Where:** Multiple controllers:
  - `CardsController.List()` — `archivedLimit` parameter passed directly to `.Take()` with no max cap
  - `ProjectsController.List()` — `take` default 20, no max
  - `AdminController.ListUsers()` — `take` default 20, no max
  - `AdminController.ListProjects()` — `take` default 20, no max
  - `AdminController.QueryAuditLog()` — capped at 500 (good)
  - `NotificationsController.List()` — `take` default 20, no max
  - `UsersController.Search()` — `limit` default 10, no max
- **Issue:** Most list endpoints accept unbounded `take`/`limit` parameters. `EfCardRepository` applies `filter.ArchivedLimit.Value` directly to `.Take()` with no ceiling. An attacker can request `take=999999` on any paginated endpoint.
- **Impact:** Database resource exhaustion. Large `.Take()` queries consume memory and CPU on the DB server. Combined with no rate limiting, trivial to DoS the API.
- **Fix:** Add a global max page size constant (e.g. 100 for user-facing, 500 for admin). Apply `Math.Min(take, MaxPageSize)` in every controller action before passing to the service/repository. The audit log already does this correctly — replicate the pattern.

#### [MEDIUM] NtfyClient uses admin-configured URL without validation
- **Category:** SSRF / path traversal
- **Where:** `src/HydraForge.Infrastructure/Notifications/NtfyClient.cs:30` — `var url = $"{settings.NtfyServerUrl.TrimEnd('/')}/{topic}";`
- **Issue:** The ntfy server URL comes from admin-configured system settings. While admin is trusted, there is no validation that the URL uses `https://` scheme or that it doesn't point to internal network resources. The URL is used directly in `_http.PostAsJsonAsync(url, ...)`.
- **Impact:** A malicious or compromised admin could set `NtfyServerUrl` to an internal service (`http://169.254.169.254/latest/meta-data/` on AWS, or internal network services) and exfiltrate data via the notification payload. Low practical risk since admin is trusted, but defense-in-depth gap.
- **Fix:** Validate the URL scheme is `https://` (or `http://localhost` for dev). Consider maintaining an allowlist of permitted ntfy server hostnames. Add a connection test on settings save that verifies the URL is reachable and returns expected response.

#### [MEDIUM] No request body size limit on most endpoints
- **Category:** Rate limiting / DoS resilience
- **Where:** `Program.cs` — no global `MaxRequestBodySize`; only `CardAttachmentsController` has `[RequestSizeLimit]`
- **Issue:** POST/PUT endpoints for cards, projects, specs, plans, comments, and checklists accept unbounded request bodies. Spec/plan markdown content could be arbitrarily large.
- **Impact:** Memory exhaustion via large payloads. Attacker sends multi-gigabyte JSON body to `PUT /api/projects/{id}` or `POST /api/projects/{id}/cards/{cardId}/specs`.
- **Fix:** Set a global `MaxRequestBodySize` (e.g. 1 MB for most endpoints, higher for spec/plan content). Spec/plan endpoints already have `MarkdownPayloadTooLarge` error code — ensure it's enforced with a size check before deserialization.

#### [LOW] Health endpoint exposes internal status without authentication
- **Category:** Insecure configuration
- **Where:** `src/HydraForge.Server/Controllers/Health/HealthController.cs` — no `[Authorize]` attribute
- **Issue:** `GET /health` returns database connectivity status and LLM provider configuration status to unauthenticated callers. While health endpoints are conventionally public, this one reveals whether LLM providers are configured and whether the database is reachable.
- **Impact:** Information disclosure — attacker can probe infrastructure status. Knowing LLM providers are configured could inform targeted attacks on AI infrastructure.
- **Fix:** Either accept this as standard practice (most health checks are public) or add a simple shared secret/token requirement for the detailed response while keeping a minimal `/healthz` liveness probe public.

#### [LOW] No forwarded headers middleware
- **Category:** Insecure configuration
- **Where:** `Program.cs` — no `app.UseForwardedHeaders()` call
- **Issue:** When deployed behind a reverse proxy (nginx, Cloudflare, load balancer), the client's real IP is lost. `HttpContext.Connection.RemoteIpAddress` will show the proxy's IP, not the client's.
- **Impact:** Audit log entries will record the proxy IP instead of the real client IP. Rate limiting (when implemented) would apply to the proxy IP, not individual clients — one bad actor behind the same proxy could rate-limit everyone. Correlation IDs still work but forensic value is reduced.
- **Fix:** Add `builder.Services.Configure<ForwardedHeadersOptions>(options => { options.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto; })` and `app.UseForwardedHeaders()` before `app.UseAuthentication()`. Ensure the reverse proxy is configured to set `X-Forwarded-For`.

#### [LOW] Argon2 parameters are configurable but not validated
- **Category:** Weak cryptography
- **Where:** `src/HydraForge.Infrastructure/Auth/Argon2PasswordHasher.cs` — reads `MemorySizeKiB`, `Iterations`, `Parallelism` from config
- **Issue:** Argon2 parameters are configurable via `appsettings.json` / environment variables with no minimum validation. An operator could accidentally set `Iterations: 1` or `MemorySizeKiB: 1024`, drastically weakening password hashing.
- **Impact:** Weak password hashes if misconfigured. Current defaults (64 MiB memory, 3 iterations, 4 parallelism) are reasonable but not enforced.
- **Fix:** Add startup validation: `if (options.Iterations < 2) throw new InvalidOperationException(...)`. Enforce minimums for memory (≥ 32768 KiB) and iterations (≥ 2).

#### [LOW] AuthController.Login has no [AllowAnonymous] — implicit only
- **Category:** Broken authentication / authorization
- **Where:** `src/HydraForge.Server/Controllers/Auth/AuthController.cs:10` — class has no `[Authorize]`, `Login()` has no `[AllowAnonymous]`
- **Issue:** The `Login` endpoint is publicly accessible only because the controller class lacks `[Authorize]`. If someone adds `[Authorize]` to the class later (for consistency with every other controller), login would break silently — returning 401 instead of processing credentials. Every other controller in the project has explicit `[Authorize]` on the class.
- **Impact:** Future regression risk — not currently exploitable. A refactor that adds class-level `[Authorize]` would lock everyone out.
- **Fix:** Add `[AllowAnonymous]` explicitly on the `Login()` method. This makes the intent clear and prevents accidental lockout during refactoring.

#### [LOW] CORS allows credentials with configurable origins
- **Category:** Insecure configuration
- **Where:** `src/HydraForge.Server/Program.cs:51-56`
- **Issue:** CORS is configured with `AllowCredentials()` and origins from config (`Cors:AllowedOrigins`). Default is `http://localhost:3000` — safe for dev. But if an operator sets `AllowedOrigins` to `*` in production, the combination of wildcard origin + credentials is rejected by browsers (spec violation), but the misconfiguration itself indicates a misunderstanding that could lead to overly permissive settings.
- **Impact:** Low — current defaults are safe. Risk is operational: an operator might add a broad origin pattern without understanding the credentials implication.
- **Fix:** Add validation at startup: if any origin contains `*` and `AllowCredentials()` is enabled, log a warning or throw. Document in `.env.example` that origins must be specific when using credentials.
